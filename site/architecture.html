Identity and trust

Delegation, not propagation and not minting

Every service that calls another presents a JWT issued by Keycloak. Services are OAuth clients with service accounts (non-human identities); engineers are realm users. Roles live in realm_access.roles.

An agent should not hold the caller's rights. Before each agent call, Maestro asks Keycloak to exchange the caller's token (RFC 8693) for an on-behalf-of token: same subject, but addressed to that one agent, carrying that one domain role, valid five minutes, with Maestro recorded as the carrier. Keycloak refuses to delegate a role the caller lacks, so authorisation stays end-to-end per caller and Maestro still cannot escalate. Non-human identity stays in one place (Keycloak) with one mechanism (JWT), which is why the lab starts with MCP rather than A2A.

The gateway is the policy enforcement point: JWT validation against Keycloak's JWKS, tool-level RBAC on the roles the badge carries, metrics, audit. Each domain agent verifies the token again and insists it is addressed to it, so bypassing the gateway, or re-using a token minted for another agent, buys nothing.

Shared monitoring

Expert knowledge of what to look for

Everything exports natively

Prometheus (kube-prometheus-stack) scrapes both gateways, Valkey's and Kafka's exporters, the sample application and the agents themselves. No synthetic metrics: the faults are real, so the signals are real.

One dashboard per domain

Grafana is provisioned with a fleet overview plus domain-apim, domain-cache, domain-messaging and the member portal. Agents cite panels by deep link so a responder opens exactly what the agent read.

The skill knows the panel

Each domain's SKILL.md documents the panel-by-panel reading of its dashboard, the PromQL for each failure mode, and what "implicated" means for that domain. That is the "expert knowledge of the monitoring tool" an enterprise agent must carry.

North star

MCP with JWT today, A2A when identity is ready

Why MCP now

MCP needs nothing beyond a bearer token on each call. The same JWT the consumer already holds authorises every hop, and one gateway policy filters tools per caller. There is no agent card to sign, no task lifecycle to secure, no second identity model to run.

What changes for A2A

agentgateway already routes A2A. When agent cards and long-running task lifecycles are needed, the migration is a routing policy on the same gateway, the same JWT rules, and one adapter per agent. Maestro's consolidation logic does not change. Recorded in ADR-0004.
